# Git для QA: diff, blame и поиск регрессии через bisect

Тема: Git, regression, diff, blame, log, bisect, good commit, bad commit, регрессия, воспроизведение. Проверка источника: 2026-10-15.

## Какие доказательства нужны

Регрессия — ранее работавшее поведение, которое сломалось после изменения. Для поиска причины нужны воспроизводимый сценарий, известный good commit и bad commit, одинаковые данные и окружение. Ошибка окружения не должна автоматически считаться плохим результатом проверки продукта.

`git diff` показывает различия, `git log` — историю, `git blame` связывает строки с последним изменившим их commit. Blame не доказывает причину дефекта и не оценивает человека: изменение могло лишь проявить прежнюю ошибку.

## Учебный bisect

В отдельной чистой копии проекта выбрать реальные проверенные ревизии вместо GOOD_COMMIT/BAD_COMMIT:

```sh
git bisect start
git bisect bad BAD_COMMIT
git bisect good GOOD_COMMIT
```

Git выбирает промежуточную ревизию. На ней собрать приложение и выполнить тот же сценарий; отметить `git bisect good` или `git bisect bad`. Если ревизия не собирается или не может быть проверена по независимой причине, использовать `git bisect skip`. После завершения — `git bisect reset`.

Bisect ищет границу в заданной истории. Если результат теста случаен, среда меняется или было несколько исправлений и повторных поломок, вывод может быть неоднозначным. Пропущенные commits тоже способны оставить несколько кандидатов.

## Практика и ошибки

В отчёт добавить точные good/bad revisions, сценарий, фактический результат и подозрительный diff; затем подтвердить причинность проверкой изменения. До checkout сохранить свою работу; bisect меняет рабочую ревизию. Не запускать его поверх несохранённых правок пользователя.

Вопрос: «Что делать, если тест flaky?» Сначала стабилизировать критерий или определить процедуру повторов, которая позволяет надёжно классифицировать ревизию. Автоматический бинарный поиск на случайном oracle даёт ложную уверенность.
