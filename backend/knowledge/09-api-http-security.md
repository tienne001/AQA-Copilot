# API и HTTP: методы, статусы, идемпотентность и авторизация

Тема: API, HTTP, REST, GET, POST, PUT, DELETE, status code, idempotency, authentication, authorization, Bearer, контракт. Проверка источников: 2026-10-15.

## Семантика HTTP

GET получает представление ресурса. Safe означает, что клиент не просит изменить состояние; служебное логирование всё ещё возможно. Idempotent означает одинаковый предполагаемый эффект повторов и одного запроса, а не одинаковое тело или статус ответа. GET, PUT и DELETE идемпотентны по семантике HTTP; POST не имеет общей гарантии идемпотентности.

201 означает создание ресурса, 202 — принятие без гарантии завершения, 204 — успешный ответ без содержимого. 401 относится к отсутствию действительных authentication credentials и включает challenge; 403 — отказ выполнить запрос. Конкретный API может скрывать существование чужого ресурса через 404. Ожидания фиксируются в контракте.

## Учебная проверка API

Для создания заказа проверить: статус, Content-Type, JSON-схему и значения, запись заказа, повтор чтения по id. Негативные проверки: пропущенное поле, неверный тип, выход за границы, отсутствующий/истёкший токен, доступ пользователя B к заказу A. Список и пагинацию проверять на пустом наборе, границах страницы и стабильном порядке.

Если контракт принимает idempotency key, повторить тот же запрос с тем же ключом и проверить один бизнес-эффект; поведение при том же ключе с другим телом уточняется контрактом. Повтор POST после сетевого timeout без такого механизма способен создать дубликат: timeout клиента не доказывает отмену обработки сервером.

## Токены и ошибки

Bearer означает, что владения токеном достаточно для доступа в пределах его полномочий. Передавать его через `Authorization: Bearer ...` по защищённому соединению; не помещать в URL, логи и репозиторий. Authentication отвечает «кто?», authorization — «что разрешено?».

Вопрос: «Достаточно status 200?» Нет: нужны контракт, тело, права и бизнес-постусловия. Проверка только статуса пропустит неправильного пользователя или неверные данные.

Источники: [RFC 9110 HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html), [RFC 6750 Bearer token usage](https://www.rfc-editor.org/rfc/rfc6750.html).
