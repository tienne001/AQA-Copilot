# SQL: JOIN, GROUP BY, NULL и проверка данных

Тема: SQL, PostgreSQL, SELECT, INNER JOIN, LEFT JOIN, GROUP BY, HAVING, COUNT, NULL, дубликаты, агрегаты. Проверка источников: 2026-10-15; синтаксис PostgreSQL.

## Как читать запрос

Практическая логическая модель SELECT: получить строки FROM/JOIN, отфильтровать WHERE, сгруппировать GROUP BY, отобрать группы HAVING, вычислить результат SELECT, отсортировать ORDER BY. Это объяснение семантики, не обязательный физический порядок выполнения оптимизатором.

INNER JOIN возвращает совпавшие пары. LEFT JOIN сохраняет все строки слева и добавляет NULL справа при отсутствии совпадений. Условие по правой таблице в WHERE может удалить эти строки; если нужно сохранить отсутствующие совпадения, внимательно выбирать условие ON.

NULL означает неизвестное/отсутствующее значение. Проверять через `IS NULL`, не `= NULL`. WHERE оставляет только true; unknown не проходит. `COUNT(*)` считает строки, `COUNT(column)` — ненулевые значения. JOIN «один ко многим» размножает строки и может исказить SUM.

`COUNT(DISTINCT column)` считает различные ненулевые значения. `COUNT(1)` считает каждую строку, потому что константа 1 не NULL, и по смыслу даёт тот же результат, что `COUNT(*)`. На пустом наборе COUNT возвращает 0; SUM и AVG возвращают NULL. Ноль для суммы при необходимости задают явно через `COALESCE(SUM(column), 0)`.

## Учебный запрос

Есть `users(id)` и `orders(id, user_id, status, total)`. Требуется каждый пользователь и число оплаченных заказов, включая ноль:

```sql
SELECT u.id, COUNT(o.id) AS paid_count
FROM users AS u
LEFT JOIN orders AS o
  ON o.user_id = u.id AND o.status = 'paid'
GROUP BY u.id
ORDER BY u.id;
```

Предполагается, что `orders.id` не NULL. Перенос `o.status = 'paid'` в WHERE исключит пользователей без оплаченных заказов. Для групп с двумя и более заказами добавить `HAVING COUNT(o.id) >= 2` перед ORDER BY.

## Ошибки и тренировка

`DISTINCT` может скрыть ошибочную кардинальность JOIN. Сначала объяснить, откуда взялись дубликаты. Без ORDER BY порядок строк не гарантирован; для стабильной пагинации нужен однозначный порядок. Значения в запросы приложения передавать параметрами, а не конкатенацией пользовательского текста.

Вопрос: «Почему COUNT(*) после LEFT JOIN показывает 1 при отсутствии заказов?» Потому что существует одна результирующая строка пользователя с NULL-полями заказа; `COUNT(o.id)` вернёт ноль.
